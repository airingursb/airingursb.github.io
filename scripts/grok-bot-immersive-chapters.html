CHAPTER 01

两个公式 — Agent 系统到底是什么

Two formulas — what is an agent system, really?

两个公式，一具骨骼

two formulas, one anatomy

用户在 Grok Bot 里看到的是「一个会写代码、会搜网页、会开终端的聊天窗口」。但把 Electron 外壳掀开，你看到的不是「一个大模型」，而是一组可替换的进程 + 一套内容寻址的状态机 + 一棵树状的子 Agent 协作图。

在读任何具体文件之前，先记住两个公式——它们是后面 15 章的骨骼。

In Grok Bot the user sees one chat window that codes, browses, and runs shells. Peel the Electron shell and you don't find "one big model" — you find replaceable processes + a content-addressed state machine + a tree of collaborating subagents.

Before any file path, fix two formulas in your head — the skeleton for the next 15 chapters.

CHAPTER 02

四层进程 — 从 Renderer 到 Box

Four layers — renderer to box

renderer → coordinator → host → box-exec-daemon

README 里的架构图只有五行。展开来看，每一层都有明确的不信任边界：

  1. Renderer + preload（electron-preload/）：UI 只能通过 COORDINATOR_METHOD_TABLE 调用 sendPrompt、getSubagents 等 RPC，不能直接碰 host。
  2. electron-main：拥有窗口、密钥、MCP 桌面运行时；spawn node-agent-coordinator 子进程；通过 carrier 把 bootstrap 凭证交给 coordinator。
  3. node-agent-coordinator：SSE 网关客户端 + inference router + MCP OAuth 转发。非 Cursor provider 时，不走远程 host 的 AnysphereAgent，而是在本地模拟 transcript 事件形状。
  4. host (sand-host)：扩展图（turn-execution、inference、transcript…）+ SandAgentRunner + AnysphereAgent。真正执行 tool loop 的地方。
  5. box-exec-daemon：ConnectRPC ExecService / ControlService，在沙箱 VM 里跑 shell、读文件、加载 MCP server。

The README diagram is five lines. Each layer is a trust boundary:

  1. Renderer + preload: UI only calls coordinator RPCs like sendPrompt, never talks to host directly.
  2. electron-main: owns windows, secrets, MCP desktop runtime; spawns coordinator child.
  3. node-agent-coordinator: gateway SSE + inference router; non-Cursor providers fake transcript events locally.
  4. host: extension graph + SandAgentRunner + AnysphereAgent — the real tool loop.
  5. box-exec-daemon: sandboxed shell/file/MCP via ConnectRPC.
source/node-agent-coordinator/main.ts · composeCoordinator()hub
// 1. carrier bootstrap · 2. control port → electron-main // 3. CoordinatorGatewayClient (SSE + HTTP) // 4. renderer port server · 5. local-exec supervisor // 6. inference router · 7. MCP OAuth + client-side-tool-v2 relay

设计取舍：Coordinator 是传输适配器，不是第二大脑

Tradeoff: coordinator is transport, not a second brain

Renderer 永远不直连 host。多一跳延迟，换来：统一鉴权、防火墙友好、以及把 Claude/Codex/OpenRouter 路由在桌面侧完成而不改 UI。

Renderer never talks to host directly. Extra hop buys unified auth, firewalling, and desktop-side routing for alternate providers without UI changes.

CHAPTER 03

Agent 数据模型 — Metadata、Protobuf 与 Blob

Agent data model — metadata, protobuf, blobs

AgentMetadata · ConversationStateStructure · content-addressed KV

「一个 Agent」在代码里是两层结构：

  • AgentMetadata（packages/agent-kv/agent-store.ts）：agentId、name、mode（default/plan/debug/search）、latestRootBlobId、可选 subagentInfo（若此 Agent 本身是子 Agent）。
  • ConversationStateStructure（proto/agent/v1/agent_pb.ts）：真正的对话状态——turns[]、todos[]、summary、subagentStates{}、subagentStateRefs{}、fileStatesV2、tokenDetails 等。

Checkpoint 时，整棵状态树序列化成 protobuf blob，按内容哈希存入 BlobStore；latestRootBlobId 指向最新根。这是 Git 式不可变历史——resume、分支、同步都建立在 blob 图上。

One agent is two layers:

  • AgentMetadata: id, name, mode, latestRootBlobId, optional subagentInfo if this agent is a child.
  • ConversationStateStructure: turns, todos, summary, subagent maps, file states, token details.

Checkpoints serialize to content-addressed protobuf blobs — Git-like immutable history for resume and sync.

source/packages/agent-kv/agent-store.tstypes
export interface AgentSubagentInfo { parentAgentId: string; rootParentAgentId: string; toolCallId: string; typeName: string; }

子 Agent 状态：inline vs ref

Subagent state: inline vs ref

subagentStates{} 存小状态；大的进 subagentStateRefs{}（blob id）。恢复时 resolveSubagentPersistedStates() 并发拉取（最多 8 路），缺 blob 且无 inline 则 BlobNotFoundError。

Small states stay in subagentStates{}; large ones use subagentStateRefs{}. resolveSubagentPersistedStates() loads up to 8 concurrent blob fetches.

CHAPTER 04

Turn 执行链 — 从 sendPrompt 到 settle

Turn execution — sendPrompt to settle

TurnExecutionRegistry · SandAgentRunner · createTurnSettle

一次用户消息不是「调一次 completion API」。在 host 里是一条受控流水线：

  1. Gateway sendPrompt → transcript send-pipeline 追加用户条目
  2. turn-execution.createRunner(session, hooks) — 必须通过已 bind 的 TurnExecutionRegistry（双 bind 直接抛错，防止两个 runner 抢同一 session）
  3. SandAgentRunner.run() → createTurnAgentRunContext()（推理 session、summarization session、shell-watch）
  4. AnysphereAgent.runStream() — 最多 ~1000 步 tool loop
  5. createTurnSettle().onTurnCompleted() — checkpoint + transcript 两阶段提交 + post-turn memory

A user message is a controlled pipeline in host: send-pipeline → turn-execution registry (fail-closed double-bind) → SandAgentRunner → AnysphereAgent (~1000 tool steps) → turn settle checkpoint.

source/host/extensions/turn-execution/turn-execution-service.tsguard
export const DOUBLE_BIND_MESSAGE = "Sand turn execution is already bound..."; bindExecutor(executor) { if (this.executor !== undefined) throw new Error(DOUBLE_BIND_MESSAGE); }
Why Gateway 可能在 composition root 就绪前就 kickstart；单 bind 保证「一个 agent session 只有一个 runner」，失败要 loud，不要 silent race。 Gateway may kickstart before composition is ready; single-bind ensures one runner per session — fail loud, not silent race.
CHAPTER 05

AnysphereAgent — 动作分发与 Tool Loop

AnysphereAgent — action dispatch & tool loop

packages/agent/index.ts · actionHandlers · SummarizationOrchestrator

AnysphereAgent 是包内的 Agent 根。构造函数注册一组 ActionHandler，runStream 按 action.action.case 分发：

  • userMessageAction — 主路径：可能先 compact，再组 prompt，再 tool loop
  • resumeAction / summarizeAction / cancelAction
  • backgroundSubagentAction — 子 Agent 完成时合成消息唤醒父 Agent
  • backgroundTaskCompletionAction、executePlanAction、goalContinuationAction …

Tool 执行走 RedactedPromptToolExecutor（隐私 redaction 贯穿）。SummarizationOrchestrator 在 user/resume/background 路径共享，决定何时 self-summary vs LLM summary。

AnysphereAgent registers action handlers; runStream dispatches by action.case. Tool loop via redacted executor; shared SummarizationOrchestrator for compaction triggers.

CHAPTER 06

工具与 MCP — ResourceAccessor 模型

Tools & MCP — ResourceAccessor model

host-runner-composition · box-exec-daemon · routed-mcp-bridge

工具不直接 exec() 操作系统。它们通过 ResourceAccessor 申请远程执行器：

  • shellStreamExecutorResource → box-exec ConnectRPC 流式 shell
  • mcpExecutorResource → 工作区 MCP 工具调用
  • subagentExecutorResource → spawn 子 Agent
  • requestContextExecutorResource → 组装 workspace 上下文

每轮 turn-toolset.ts 组装工具面：read/write/edit、shell、web、MCP meta、CloudAgent、子 Agent 管理工具。Group room 成员有裁剪版 toolset + guardrail prompt。

Tools acquire remote executors via ResourceAccessor — shell stream, MCP, subagent spawn, request context. Per-turn toolset assembled in turn-toolset.ts; group members get restricted surfaces.

Inference router 走 Claude/Codex 时，routed-mcp-bridge.ts 在 coordinator 侧建临时 MCP 桥，把 listRoutedMcpTools / executeRoutedMcpTool RPC 回 host——不在 coordinator 里再跑一遍 MCP server 进程。

For routed providers, routed-mcp-bridge.ts proxies MCP back to host instead of duplicating server processes in coordinator.

CHAPTER 07

Task 工具 — 子 Agent 的「唯一官方分叉口」

Task tool — the official fork for subagents

packages/agent/tools/task.ts · task-subagent-preparation.ts

多 Agent 协作的第一性接口是 Task 工具（不是随便再起一个 chat session）。流程：

  1. prepareTaskSubagent() / resolveTaskSubagentConfig() 解析 subagent_type、model、environment（LOCAL vs CLOUD）
  2. 为子 Agent 构造独立 AnysphereAgent（可覆盖 systemPrompt、tools、modelId）
  3. Foreground：子 Agent 的 InteractionUpdate 经 TaskToolCallDelta 流式推到父气泡
  4. Background：注册到 subagent-runtime，完成时 BackgroundSubagentActionHandler 注入父对话

Lineage：computeSubagentRequestId(toolCallId) → subagent:{toolCallId}，HTTP 头带 x-parent-request-id / x-parent-agent-tool-call-id 供遥测与计费归因。

Multi-agent collaboration's primary API is the Task tool: prepare config → isolated AnysphereAgent → foreground streaming deltas or background completion actions. Lineage via subagent:{toolCallId} request ids.

source/host/runner/subagent-runtime.tslineage
export function computeSubagentRequestId(toolCallId: string): string { return toolCallId.length > 0 ? `subagent:${toolCallId}` : "subagent"; }
Steering MessageSubagent 向已在跑的后台子 Agent 追加指令，而不是 duplicate spawn。Multitask 模式里这是「一个 stream 一个 executor」的关键纪律。 MessageSubagent steers running background subagents instead of spawning duplicates — core discipline in multitask mode.

CHAPTER 09

Multitask — 父 Agent 当调度员，Executor 当苦力

Multitask — parent dispatches, executor sweats

host/sand-multitask.ts · Statsig gate · TodoWrite as coordination memory

这是 Grok Bot 里最像「多 Agent 编排」的产品化模式（实验 gate：multitask）。核心思想写在 SAND_MULTITASK_PROMPT_SECTION 里，值得整段背诵：

  • 父 Agent 回合必须短——秒级回复用户；重活全部 Task(subagent_type: "executor")
  • 独立任务各起一个 executor，并行；同一 stream 的 follow-up 用 MessageSubagent steer，禁止 duplicate
  • Executor 启动空白——dispatch prompt 必须自包含目标、上下文、成功标准
  • TodoWrite 是跨并行 stream 的外部记忆：pending / in_progress / completed 与 wake 时 reconcile
  • 对用户不可见「dispatching / delegating」等词——产品人格是「一个人同时干很多事」

The multitask experiment makes the parent a dispatcher: short turns, heavy work via executor subagents, parallel independent streams, TodoWrite as coordination memory, invisible orchestration vocabulary to the user.

source/host/sand-multitask.tsprompt
"You are the dispatcher, never the workhorse." "Never do heavy work inline." "TodoWrite is your task queue and your multitasking memory."
Tradeoff 并行度靠 prompt 纪律 + Todo 状态，不是硬调度器。好处：灵活、可 A/B；风险：模型偶发 inline 重活或忘记 reconcile todos。 Parallelism is prompt discipline + todos, not a hard scheduler — flexible but model-dependent.

后台子 Agent — 注册表、完成与唤醒

Background subagents — registry, completion, wake

subagent-runtime.ts · onPendingWakeArmed · SUBAGENT_REVIVAL_EVENT

createSubagentRuntime(host) 维护三张表：

  • subagentSessions — 可 run / interrupt 的会话
  • backgroundSubagentRuns — 进行中的 Promise

CHAPTER 13

Summarization — 长对话的三层压缩

Summarization — three tiers of compaction

pipeline.ts · summarization-handler.ts · summarization-orchestrator.ts

多 Agent 协作会让 transcript 爆炸式增长。压缩管线：

  1. partition — 头部分要 summarize，尾部 preservedTailMessages 必须保留（且尾部形状 invariant：以 user 开头、中间不再出现 user）
  2. generateSummary — 默认 gemini-2.5-flash，失败则 deterministic fallback
  3. assemble — [summary message] + preservedTail；durable blocks 保留 skill/todo/plan

SummarizationOrchestrator 还在 token 阈值前做 cheap self-summary，并支持 background summarization（空闲时异步 compact）。summaryArchives[] 保留历史压缩版本。

Partition → LLM/deterministic summary → assemble with preserved tail. Orchestrator adds self-summary and background modes; archives keep compaction history.

Agent Store Sync — 本地 Index 与云端 BCS

Agent store sync — local index & cloud BCS

agent-store-sync/ · SyncRoundScheduler · path-first

CHAPTER 15

Inference Router — 同一 UI，四条推理后端

Inference router — one UI, four backends

node-agent-coordinator/inference-router.ts

Settings → Router 可选 Cursor / Claude Code / Codex / OpenRouter。当 provider ≠ cursor 时，coordinator 拦截 sendPrompt：

  1. 追加用户消息到本地 inference-router-transcript.json
  2. 向 renderer 发 transcript SSE（形状与官方一致）
  3. runRoutedProviderText() + MCP bridge 跑 tool loop
  4. 流式 assistant delta，落盘，清除 activity

这意味着多 Agent 的完整语义（子 Agent、blob checkpoint）主要在 Cursor 路径；路由路径是「UI 兼容层」，边缘行为可能分叉。

Non-Cursor providers intercept sendPrompt, persist local transcript, fake SSE shape, run routed tool loop — UI-compatible layer, not full host semantics.

### 一台不关机的电脑，还不是一位可靠的同事

这周的 Personal Agent 产品有一个共同动作：把 AI 从一次对话里搬出来，放进一台持续在线的电脑。你离开之后，它还能整理文件、运行程序，等到指定时间再做下一件事。Founder Park 的文章把这轮变化梳理得很清楚：产品有的住在独立 App，有的通过短信和邮件出现，有的干脆是一支有名字的 Bot 团队；底层则逐渐收敛到云端电脑、长期记忆和外部工具连接。[12](#source-12)

这解释了它为什么令人兴奋。以前我们把问题带到聊天框，现在可以把一段工作留给它。但也正是在这里，评价标准变了。回答一条消息，只需检查眼前的答案；把任务托付一晚，第二天需要知道它做到了哪里、哪些结果可信、剩下的工作由谁接手。

**常驻解决的是“谁继续运行”，交付解决的是“谁能接受这个结果”。** 我更在意后一件事。一个助手连续忙了八小时，如果回来仍要从头核对所有过程，那只是把劳动换成了监督。

### 从“帮我管生活”，缩小到一件可以结束的事

Founder Park 提到退订服务这样的切口：任务有对象，也有明确结果。相比笼统的“管理我的生活”，我们更容易判断一项订阅是否取消、是否收到确认、下一期是否仍会扣款。真正让人愿意再次委托的，往往是这样一次完整的小闭环。

Dots 与 Jev 的社区指南讨论了另一种分工：快速决策层负责选择、评分和分流，能力更强的模型负责执行。Grok Bot 的入门教程则列出定时整理、内容复用、支持请求分诊等例子。它们都让“持续工作”有了具体形状，但任务便宜不便宜，要连同重试、升级、核查和人的时间一起计算，不能只比较一次模型调用。[02](#source-2) [04](#source-4)

拿我自己的周刊举例，比起“今晚帮我做一期”，更有用的委托是：“把这个时间范围的收藏全部归档，合并同题材料，给每个判断标来源，交一份手机能读的草稿。”前者让 Agent 猜什么叫好；后者至少让我们可以检查是否遗漏、引用是否支撑论点，以及页面是否可读。**清楚的完成条件，会直接减少后面的来回确认。**

### 团队规模之前，先把交接做一次

这周收藏的 Grok Bot 团队模板，把参谋长、功能负责人和验证者分开。公开配图里最有价值的设计，是提交工作的人不负责宣布自己验收通过；验证要指向可检查的产物，例如复现步骤、测试结果、截图或运行记录。原帖展示的是模板的一页，不能把它当成一套已经验证有效的完整组织方案。[06](#source-6)

不过，这个分工足够启发我们：多 Agent 协作真正增加的不是“脑子”，而是交接次数。采集说链接齐了、写作说稿子好了、排版说构建通过了，三句话仍可能拼不成一期好周刊。需要有人把验收条件串起来，并能指出哪个环节还没有证据。

飞书接入教程降低了把这些角色带进群聊的门槛。接通之后，下一步应当是让消息指向同一项任务：任务归谁，结果存哪里，哪些决定需要编辑。这些信息如果只散落在聊天记录里，人很快就会成为每个 Agent 的人工路由器。[19](#source-19)

### 断线之后，别让“再来一次”成为默认答案

Pi 的 Durable Objects 教程提供了更底层的例子：把会话、任务和请求回执保存在持久状态里；请求重发时，先确认之前是否已经创建过对话；恢复检索时，找回原先的子任务。检索子代理还排除了过去的检索产物，避免一次摘要被下一轮当成原始证据。[30](#source-30)

这里最容易混淆的是两种恢复：恢复计算，和重复执行一个外部动作。重新分析一份文件通常可以重来；已经发过的邮件，不能因为没有收到回执就再发一次。教程也提醒，闹钟可能重复触发，外部调用并不天然只有一次。**可靠的系统要能够承认“结果未知”，然后先查证，再决定是否重试。**

<!-- visual: recovery -->

这也是我对常驻 Agent 的期待：少一点“我一直在努力”的汇报，多一点“你可以从这里接着做”的确定感。AIGC Weekly #192 把 Personal Agent、协议与产品更新放在同一期里，适合作为本专题的延伸阅读；保存的 Newsletter 片段可能不完整，因此这里不据它补写具体协议能力。[15](#source-15)

### Scion：代码多了，最先吃紧的可能不是模型

Anthropic 的工程文章讲了一次很不寻常的基础设施改造。公司报告，单日合并次数从 5 月约 2,500 次升到 9 月超过 30,000 次，CI 每天约有 2,500 万次检出。在这个规模下，反复搬运历史和工作副本，成了实实在在的计算与网络负担。Scion 把更多历史查询、合并等工作放到服务端，客户端按需取得当前任务所需的数据。[13](#source-13)

中文解读与英文工程原文是这周两条独立收藏，这里放在同一专题，保留两个阅读入口。文章中的“约 200 倍”比较的是版本控制基础设施的 CPU、内存占用，不能写成程序员产出提高了 200 倍。[16](#source-16)

<!-- visual: scion -->

我觉得它最值得借鉴的地方，是提问方式。先观察工作负载如何变化，再判断旧假设是否还成立。一个以人工开发为主的小仓库，与大批常在线 Agent 和 CI 作业面对的瓶颈并不相同。Scion 是特殊规模下的工程选择，普通团队不必据此换掉 Git。

但普通团队可以立刻做另一件事：把一次交付的时间拆开。写代码用了多久，等待测试多久，卡在审查多久，上线后又返工多久？假如生成代码只占很小一段，让它再快一倍，也不会自动让整件事快一倍。**当执行越来越便宜，队列和返工会变得越来越显眼。**

### 让最短的路，就是正确的路

@poteto 的原帖、以及这周收藏的中文解读，把信任 Agent 的投入顺序放在代码结构、自动检查、文字指导和人工审查上。我的理解是：与其反复提醒“这里不能这样改”，不如让接口、类型和模块边界尽早暴露这个错误。[32](#source-32)

这不是说人可以不审，而是把人的注意力留给工具难以回答的问题。类型检查可以发现字段不匹配，却不知道这个字段是否该被收集；端到端测试可以重现一条操作路径，却不能替产品决定这条路径是否合理。

<!-- visual: trust -->

omp 把语言服务、调试器和编辑工具放进同一工作环境，体现了这种思路：让 Agent 获得真实的程序反馈，而不是只靠文字猜测。e2e 的迁移技能则建议按功能保留新旧套件对照与迁移记录。前者让错误更早显形，后者提醒我们：换了验证方式，原来的验证标准不能悄悄丢掉。[26](#source-26) [29](#source-29)

### 状态、会话和记忆，分别留下什么？

Pi 1.1.0 的 Program Status Protocol 让终端知道程序正在工作、阻塞还是完成；Tern 把会话持久化与跨设备继续工作放到前台；Hy Memory 将聊天、工作和编码记忆区别对待。这三条产品阅读不必各写一篇长报告，却恰好补齐了交接中的三个位置。[05](#source-5) [09](#source-9) [25](#source-25)

“完成”状态帮助人发现该看结果了；会话记录帮助人回到现场；记忆则应该帮助人理解为什么这样做。它们都不能独自代替验收。尤其是记忆，**记住一个结论，还要记住它何时成立、后来是否被推翻。** 我会用“上周试过、后来回滚的方案”检验它，而不是只问能装多少历史。

### 周日补记：把需求也接进来

腾讯技术工程的文章，把 AI 研发从编码推进到需求澄清、技术方案、审查和知识沉淀。一个具体做法是对知识设置有效期，过期进入复核；如果 Agent 发现知识与当前代码冲突，再反馈给平台。比起知识库越来越大，这种“旧答案如何退场”的设计更值得带走。[33](#source-33)

这是 10 月 18 日新增阅读。它也给本专题添了一个反问：如果需求没有统一、负责人没有更新，自动执行会不会只是更快地放大旧的误会？流程改造的目标应当是减少这些误会，而不是把每个旧环节都配上一个 Agent。

### IdeaScientist：让灵感有一条可追溯的来路

研究 Agent 容易把“提出很多想法”当成进展。IdeaScientist 把构思拆成找研究缺口、跨领域找相似问题的解法、形成提案三个角色，并用限定时间之前的文献，评估它提出的方向与后来人类论文的接近程度。论文链接与社区解读都保留在来源中。[07](#source-7) [论文](https://arxiv.org/abs/2610.04074)

这个设定有意思，因为它逼系统解释“为什么想到这里”。但接近后来出现的研究方向，只能为构思能力提供一种证据；它还没有替提案做实验，也不能证明结论正确。我的阅读重点是那条迁移链：借来的机制与当前问题是否真的共享结构，还是仅仅共享几个词？

### Evo²：改进工具的人，也开始学习

Evo² 将两种改进放进循环：一边修改 Agent 的提示、工具和上下文组织方式，也就是 Harness；一边用这些修改及执行结果训练提出修改、诊断结果的模型。它的贡献在于把“改环境”和“改模型”连接起来，而不是又多了一份神奇提示词。[20](#source-20) [论文](https://arxiv.org/abs/2610.13025)

<!-- visual: research -->

对使用者来说，这带来一个更务实的问题：提升究竟来自哪里？如果模型、运行环境和测试样本一起变了，很难知道哪一项值得保留。我会要求一次只对照一个改动，并把没参与迭代的任务留到最后验收。论文报告的基准结果属于其具体实验；将来换成我们自己的任务，还要重新检验。

### AI 研究 AI：解释必须能冒失败的风险

机器之心收藏介绍了 Nick Cammarata 的可解释性工作：先让 Agent 根据神经元响应提出解释，再让另一个 Agent 构造应当触发或不该触发的样本，交回网络测试。它改变的首先是研究规模——更多假设能被提出，也能被更快地反驳。[27](#source-27)

“约 90% 的神经元有主要功能”在报道中有模型、阈值和定义范围，不能扩大成整个模型已经被解释。真正值得借鉴的是：**好的解释应该预测没见过的情况，并允许实验把它推翻。** 一个听起来顺畅的故事，如果不会在任何结果下失败，就很难成为研究结论。

### 自复制与防蒸馏：别把不同层次的证据揉成一句话

Anthropic 的自复制研究测试了在不同设备建立推理的能力，也在简化环境中检验串联过程。局部步骤成功、受控流程成功、现实中的自主传播，是三个层次。论文中的简化访问条件不能在转述时被省去。[11](#source-11)

同周的防蒸馏文章讨论减少未经授权的大规模能力提取，公司给出的降幅是其防御评估，不是“所有数据都安全”的证明。对于依赖上游模型的工作流，这提醒我们持续检查服务接口与数据政策，而不是把当下可访问的输出视为永久不变的资源。[10](#source-10)

<!-- visual: evidence -->

这几篇放在一起，我看到的不是一条“AI 会自己变强”的直线。提出想法、改进方法、解释机制、约束行为，各有不同的验证对象。把它们分清，才能知道哪里发生了进步，哪里仍需要人来做实验与判断。

### 聊天记录能带走，熟悉的回应呢？

APPSO 的陪伴产品文章，从服务经营变化谈到一个容易被忽略的问题：导出聊天记录，只保存了过去发生过什么；下一次回答还依赖角色设定、基础模型、记忆选择和服务策略。本文关注这一产品问题，文中个别公司的破产与交易消息未经本刊独立核实，不作为本期新闻结论。[17](#source-17)

这与工作 Agent 并不是两件完全无关的事。我们把计划、偏好和理由不断交给一个长期系统，逐渐依赖的就不只是某个回答，而是它怎样理解这些历史。工作场景希望它接着推进任务；陪伴场景希望它仍以熟悉的方式回应。两者都需要比“下载一个聊天文件”更清楚的迁移说明。

<!-- visual: portability -->

我不认为产品必须承诺永远保持同一个模型。更可行的责任是让用户看见哪些记忆被保存、能够纠正它们、导出有结构的数据，并在重大变化时得到说明。**长期信任的一部分，是知道未来退出时能带走什么。**

### 当代码容易复现，产品还要留下什么？

卡兹克的文章把 AI 逆向成本下降，与软件壁垒和注意力联系起来。[08](#source-8) 它的判断很鲜明；我的补充是，复现功能、可靠运行、让人继续使用，是三项不同的工作。入口可以模仿，旧数据如何迁移、异常由谁处理、用户是否相信下一次升级，这些问题并不会随着代码变便宜而消失。

DEX #367 则换了一个角度：当机器把文章压成摘要，人再从摘要理解世界，交流会不会只剩压缩和解压缩？[18](#source-18) 这也是我对周刊的自我要求。收藏不能遗漏，但完整不等于每篇都写得一样长。编辑需要把有解释力的材料放在一起，指出分歧，再给读者回到原文的路。它应该增加理解，而不是增加阅读负担。

### 一份研究台，两条收益故事

Opus 5.5 量化研究台的长指南，比标题里的“24/7”更有价值的，是它要求先固定研究对象、证据时间和计算规则。比如一家公司在不同市场有多个上市代码，不能不加处理就算成多家公司；今天才知道的信息，也不能放进过去的决策里。先把这些问题弄清，再让 AI 跑计算，结果才有可比较的意义。[03](#source-3)

同周两条交易帖子，则分别宣称极小本金很快变成数千美元。其中“48 到 7,492”的余额差是 7,444，帖子同时提到的收益约 3,350 并不能直接对应；另一条跟单故事也缺完整可核对账本。它们是带推广链接的作者叙述，保留在来源目录里，但不据此绘制收益曲线或评判策略有效性。[21](#source-21) [23](#source-23)

这组对照让我更愿意把“允许得出什么结论”写在执行前。严谨的研究台可以得到“尚未算出”或“无法复现”；一个总要交出漂亮答案的系统，反而可能更难托付。

### 周日补记：新人从哪里学会验收？

新收录的 APPSO 文章讨论了 Anthropic 内部就业报告，并提出一个值得追问的矛盾：公司越来越强调判断力，但新人原本就是从小任务里的试错学会判断。这里是对该报道的阅读与推演，不能把一家公司的招聘变化直接当作整个行业的因果结论。[34](#source-34)

如果把所有入门任务都交给 Agent，再要求新人一来就能审它，培养路径会断掉。我更愿意尝试一种配对方式：让新人先写验收标准、预测哪里会错，再看 Agent 的方案，亲手复现一个失败，最后解释为什么接受改动。这样 AI 接手重复执行，人仍然经历形成判断的过程。组织需要同时衡量交付完成了没有，以及这次交付有没有让下一位同事更懂系统。

### 最后，把“下次从这里开始”留给自己

李睿秋的生活小技巧里，有一条与本期意外相通：留下进度，让下一次开始有入口。[01](#source-1) 我们自己也会遗忘昨天为什么停在这里。收工前记下做到哪儿、卡在哪儿、下一步是什么，既能帮同事和 Agent，也能帮明天的自己。

这就是这一期的封面：Airing 桌上放着进展、证据和下一步。把任务交出去的意义，终究是让人能放心离开，也能从容回来。

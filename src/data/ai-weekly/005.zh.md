### 从 800 行规则开始，看见真正的故障

先认识这位开发者在做什么。刘俊毅的案例是一款 Cocos Creator 微信小游戏：客户端、服务端、协议与需求分处四个仓库，不同角色要交接工作。他希望 AI 按设计实施，于是不断补充 Skill 和约束，从五百多行涨到八百多行，还列出必须遵守的规则。结果却是：步骤仍会跳过，到了下一阶段，前面的要求又可能失踪。[13](#source-13)

这不是一个干净的「长提示词对短提示词」实验，文章也不能证明 800 行是某种失效阈值。更值得看的，是作者记录的一次具体偏差：装饰摆放系统限定一次批量收回最多 20 个物品，任务拆解却写成了收回全部，执行者再忠实地把「全部」做出来。每个人都能解释自己做了什么，最终产品仍然错了。

**真正丢失的是约束的来历。** 如果实现者只能看到上一棒的摘要，它很难分辨「全部」究竟是产品决定，还是某次转述漏掉了上限。再加一句「严格遵守需求」，并不会自动把丢失的信息找回来。

<!-- visual: handoff -->

作者后来搭建了分阶段的 x-flow：保留专门角色，把设计、任务和实现连接到可核对的产物，重要节点暂停给人检查。这里最有启发性的变化，不是阶段数量更多，而是每一步有了可以回头找的依据。设计检查需求里的边界，任务引用设计，实现时再读设计，能让那个「20」在中途被发现，而不是等到用户遇到错误。

### 有些规则应该被执行，有些知识应该等用到再读

这个案例还记录了一类常见故障：某种跨分包的静态导入在编辑器里没出事，真机首次加载却崩了。把教训继续塞进提示词，等于每次都期待模型记住；写成检查脚本，则能在提交前确定地指出哪里违反了约束。[13](#source-13)

**能可靠判定的条件，应该尽量让程序判定。** 这并不要求所有产品判断都变成代码。设计好不好看、一个功能是否值得做，仍然需要上下文与取舍；文件是否存在、协议版本是否一致、导入路径是否合法，则不必反复交给语言模型猜。

<!-- visual: placement -->

图里的分法是本期据案例整理的工作方法。它同时包含两种减法：一是把随时必须遵守的约束缩短，让它们更醒目；二是把只在某个阶段有用的资料移到按需读取的位置。知识没有被丢掉，只是不用在每轮对话里重新搬家。

这也解释了为什么「有记忆」不等于「有可靠经验」。一条旧结论必须附着在适用条件、日期与证据上；代码事实最好从当前代码读取。常用但过时的建议可能很危险，罕用的发布限制却未必该删。清理规则时，要看它是否仍然正确、能否被更可靠的机制接管，而不是只看出现频率。

### 子 Agent 让工作并行，也让理解重新开始

本周另一篇关键阅读来自 Anthropic。它建议一些企业系统把高度关联的子 Agent 收回主循环，通过 Skills 与工具承载专门知识；理由之一是，多次交接会带来上下文损耗与额外等待。但它也明确保留了使用子 Agent 的场景，包括上下文隔离、独立并行和相互冲突的工具环境。[16](#source-16) [官方原文](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)

想象一个客服任务：客户既问订单，也问何时到货。若两个专员一直围绕同一订单往返，它们分工所省下的复杂度，可能抵不过共享信息、同步状态与汇总答案的成本。一个持有完整对话的 Agent，配上两个查询工具，也许更合适。**组织里有两个部门，并不意味着运行时必须有两个脑袋。**

反过来，审查者不想沿着实现者的自我解释继续走，或者两项调查能各自完成再合并，独立上下文就可能有价值。单循环也可以并行调用工具；需要并行，并不是增加子 Agent 的充分理由。

<!-- visual: agents -->

我更愿意用「信息需要待在一起吗」来判断边界。若后一步总要反复追问前一步的推理，先尝试合并；若任务有独立输入、明确产物，而且主 Agent 能检查结果，再考虑分出去。判断依据是任务之间的联系，而不是给团队画出一张看起来完整的组织图。

### 为什么另一位架构师仍然鼓励多开几个 Agent？

InfoQ 这周转述的 Carlos Kelkboom 访谈，提供了一个很好的反例：架构与代码骨架由人掌握，再让多个 Agent 探索实现；对自己已经看不懂的代码，宁愿在隔离分支重来，也不继续叠补丁。[06](#source-6)

这与减少交接并不矛盾。**几个 Agent 各自探索同一个问题，和几个 Agent 接力改写同一份需求，是两种结构。** 前者增加备选方案，代价是重复劳动与比较成本；后者分摊步骤，代价是中途信息可能变薄。它们都不能因为「开得更多」而自动变好。

腾讯案例本身也没有删掉所有专门角色。多仓库、协议边界和人工协调是它的现实条件，分阶段的流程有存在理由。把这篇经验简单概括为「不要用多 Agent」，反而会读反原文。

真正可复用的做法，是让每个额外角色说明自己的收益：它隔离了什么干扰，发现了什么独立错误，或者节省了哪段可测的等待？如果答案只是「这样更像一个团队」，那层结构还没有证明自己的必要性。

### 减法有没有做对，要看原来会的事还会不会

合并之后跑得快，只完成了一半验证。Anthropic 的示例里，合并客服角色降低了延迟，却漏掉原本能给出的送达日期；问题只在重复运行中暴露出来。[16](#source-16)

所以，值得保留的不是一张架构前后对照图，而是一小组真实任务：输入是什么、必须交付哪些结果、哪些条件不能越过、最终产物在哪里。每次只改一个结构，再检查**哪些任务从失败变成功，哪些从成功变失败**，而不只看一个平均分。

<!-- visual: evaluation -->

上期补记的腾讯研发流程文章，本周又落入正式收藏区间。它把注意力从 AI 写代码延伸到需求、协作与交付，刚好接上这个问题：局部生成更快以后，瓶颈可能转移到等待、核查和返工。[01](#source-1)

本期的减法因此有一个很实际的目标：减少那些没有改善交付的指令、角色与重复说明，让留下的检查真正保护任务。删到多少行、剩下几个 Agent，都不是终点。

### Jev 的点赞争议：可疑的热度，不是能力裁决

我们在创刊号介绍过 Jev 的决策模型。本周 AGI Hunt 的另一篇文章检查了 Hugging Face 上一个 JEV-27B-VL AutoTrust 模型的点赞账号：作者统计的 6,878 个账号中，94% 的注册时间落在模型发布前 60 天以内或发布之后。作为对照，文中几个模型的相同指标低得多。[03](#source-3)

这个分母必须保留。它既不是「94% 用户都是机器人」，也不是模型测试的错误率。作者还抽样检查了账号活动与简介，形成了对点赞真实性的怀疑，但明确表示无法确定操作者；第三方也可以给别人的模型刷赞。

<!-- visual: likes -->

这件事值得记住，因为排名往往承担了它不该承担的工作。我们看到点赞多，容易顺手推断「大家都在用」「能力经过验证」。实际上，账号行为分析能质疑热度信号，却不能替代任务评测；一次模型实测也不能洗清不正常的账号分布。

对于本刊而言，处理方式很具体：保留对 Jev 机制与适用任务的讨论，同时补上这条争议，不再把平台热度当成质量旁证。最终要验的是我们自己的分类、路由与拒答任务，不是点赞按钮。

### 98% 的物理题：更强的计算助手，怎样走向研究？

另一篇收藏的标题把结果概括成「解决 98% 世界物理难题」。回到 TheoPhysEval 论文，范围要窄得多，也因此更有研究价值：50 道未发表、答案可核验的理论物理研究级问题，允许 Agent 查文献、编写数值或符号计算脚本。论文报告，Codex 中的 GPT-6 Astra 得到最终答案的准确率为 98%，平均每题成本低于 3 美元。[07](#source-7) [论文](https://arxiv.org/abs/2610.16733)

<!-- visual: physics -->

这说明 AI 已能承担不少研究中的具体计算，值得认真改变工作方式；它没有证明模型已经能独立提出一流问题、判断研究方向，或完成同等比例的科学发现。研究者预先挑选了问题并提供可核对答案，这与在开放世界里先找出「什么值得研究」不同。

**AI 与科学家的关系，可能先在工作的切分处改变。** 如果算例、推导候选和脚本验证变得便宜，研究者可以比较更多路线，也会面对更多似是而非的结果。人的时间应该向假设选择、物理意义和独立复核移动。这里的机会不是单纯少算几页，而是让以前不值得尝试的分支变得可试；风险则是把生成答案的速度误当成积累知识的速度。

这与第 003 期数学手稿专题是同一道追问：把一份结果接进学术共同体，需要的不只是答案，还要有可检查的推理、可靠的验证，以及愿意为结论负责的人。

### 新人需要的，可能是另一种练习场

APPSO 对 Anthropic 内部工作的解读，是上期周日补记的另一篇文章，本期正式区间再次收录。它关注 AI 使用深入工作以后，初级岗位与培养方式会受到什么影响。这是对一家公司的材料和组织变化的讨论，不足以外推整个行业的招聘命运。[02](#source-2)

但它提出的矛盾值得认真面对：如果检索、初稿与简单实现被自动化，年轻人少做的这些活，过去也恰好是熟悉业务、发现错误和接受反馈的入口。不能一面减少练手机会，一面要求新人直接拥有资深判断。

我的理解是，训练目标应从「独立写出第一版」扩展到「解释为什么这样写、找出它漏了什么、知道如何验证」。例如让新人先判断一个方案，再看模型结果；让他们保留自己的失败假设，与导师讨论差异。这样 AI 能提供更多练习样本，而不只是替人交卷。

### 公益基金的重点，是股权与分配规则

另一条新闻把 Anthropic 的公益基金写成了「捐 3200 亿分给普通人」。官方公告承诺的是股权安排：经股东批准后投入 5% 股份，并设定随估值变化、由董事会酌情追加的机制；面向特定人群的直接分配只是可能探索的方式之一。它不是已经到账的现金，也没有公布面向所有人的统一发放方案。[08](#source-8) [官方公告](https://www.anthropic.com/news/public-benefit-fund)

<!-- visual: fund -->

这一步的意义，是开始讨论技术收益的所有权，而不只讨论谁用上了一个更便宜的工具。不过，股权承诺和社会保障之间还隔着治理、兑现时间、受益人选择与问责。对失去岗位的人来说，未来公司可能更值钱，并不等于今天就拥有可支配收入。

评价这类机制，后续应该看谁有资格、谁作决定、何时兑现、怎样公开结果。它也无法替代企业眼前该做的事：提供转岗训练、给新人保留学习入口，并让自动化的收益不只体现在少雇人上。

### Agent 1.0、2.0 之外，用户愿意留下什么？

特工宇宙把 QClaw、元器等产品的调整，解释为从「搭 Agent 的平台」转向「直接替人工作的 Agent」。其中的「1.0 / 2.0」是文章的叙事框架，本刊也未独立确认文中全部下架时间。[14](#source-14)

它仍然提供了一个有用的商业问题：用户究竟想拥有一个配置台，还是只想有一件事持续被做好？对开发者，编排能力可能是产品；对普通使用者，维护工作流常常只是额外劳动。

但界面更像助理，不会让持久记忆、失败恢复和可核对结果自动出现。真正值得跟踪的，是用户能否看懂它做过什么、能否带走数据、出错后能否接着做。产品换代的名字可以很快，信任仍然要靠这些小事积累。

### 一台旧 Kindle，让「自己做」重新有趣

APPSO 的作者用 GPT-6 改造一台旧 Kindle，把它变成联网相框。文章的乐趣不在于自动生成了多少代码，而在于一块真实的墨水屏会给反馈：显示效果、刷新残影、网络与设备状态，都需要人拿在手里观察，再和 AI 一起调整。[05](#source-5)

<!-- visual: kindle -->

这类小项目很适合作为 AI 的另一种使用方式：目标由自己挑，结果就在眼前，试错也可以只为好玩。模型降低了进入陌生领域的门槛，却没有替人决定为什么要做、什么样算满意。参与感不一定来自亲手敲每一行，它也来自发现问题、选择方案与看到真实物件改变。

### 一键通关之后，失落也不是矫情

卡兹克的文章写出了另一面：AI 让做产品与生成内容越来越轻松，他反而难以从中获得原来的快乐。文中借游戏开了修改器之后失去兴致的经历，描述一种目标还在、过程却被抽空的感觉；结尾没有声称解决了虚无，而是把注意力重新放在仍想探索的支线上。[15](#source-15)

这不能推出「少用 AI 才能快乐」，也不能用「换个更大目标」敷衍过去。一个人可能珍惜作品完成后的效果，也可能珍惜学习一种手艺的过程。前一种满足可以因自动化扩大，后一种满足却可能被无意删掉。

**给机器做减法，是减少无效负担；给自己留过程，是保留在乎的体验。** 两者并不冲突。可以让 AI 搬运资料、定位报错，但把观察、试验和最后的判断留给自己。也可以专门留一个不以效率计价的项目，允许它慢，允许暂时没有用途。

### 光环不会替你理解用户

地心引力这封短通讯收了法国与中美模式的文章、播客，也提到「字节掘金者：最贵的是光环」。与本期相关的，是它对应用创业的提醒：漂亮履历和资本投入，无法保证做出让人愿意使用的产品。[04](#source-4)

这与 DEX #368 对软件越来越好做、协作却未必更容易的感慨，以及 AIGC #193 收录的 Linear 产品文章，形成了一个回声：制造能力正在普及，理解具体的人、持续作出取舍，仍然需要有人在场。[11](#source-11) [12](#source-12)

所以这期最后想留下的，不是「再装一个更聪明的 Agent」。先找一件愿意反复观察、愿意承担结果的小事，把机器可以接手的重复劳动交出去，再看自己是否更靠近了它。那才是减法带来的空间。
